## What is right
- The definition is real, not a trimmed one. `fn memory` (`tools/stress.py:64-87`) walks the whole child tree and sums `Pss`, `Pss_Anon` and `Rss` from `/proc/<pid>/smaps_rollup`, so the idle figure's `processes: 3` includes the very processes that would be convenient to leave out: the frame, the WebProcess, the NetworkProcess. `src/app.rs:490-499` really does `stack.remove` **and** `view.destroy()` on close, which is why anon falls from 495.7 to 92.8 in `tabs give their memory back` and processes from 23 back to 3.
- The knobs are set where they must be, before the engine forks: `src/main.rs:61-72` sets `WEBKIT_DISABLE_DMABUF_RENDERER`, `MALLOC_ARENA_MAX` and, only when `SEARCH_LOW_MEMORY` or `Prefs::low_memory`, `WEBKIT_DISABLE_COMPOSITING_MODE`; `src/store.rs:57-64` says why it has to be there and not at runtime, and `src/panels.rs:604-605` tells the user it applies at the next launch.
- Per-tab cost really is about a fifth of idle cost and the numbers are mutually consistent: anon `495.7 - 95.2` over 20 = 20.0 MB, Pss delta 20.6 MB, both against a 212.8 MB idle baseline.
- The prose is one of the few places in this repo that refuses to round a measurement into a boast: `docs/LIMITS.md:35-40` gives the nine distinct readings (62.0, 67.1, 73.2, 86.5, 98.9, 109.8, 110.5, 117.6, 118.7), `README.md:161-167` labels the Firefox figure "one afternoon's comparison rather than a benchmark", and `docs/ARCHITECTURE.md:163` says a number written into that file would be about one afternoon.

## What costs points
- **The ~100 MB requirement is met on the metric the browser chose, and the metric is 2.1x smaller than what the system gives up.** The asserted promise is `anon_mb < 120` (`tools/stress.py:417`) and the measured 95.2 clears it, so "about 100 MB" is true of `Pss_Anon`. A person watching `top` sees 318.2 MB RSS and 212.8 MB PSS for the same tab. `docs/LIMITS.md:46-50` and `README.md:19-23` disclose both, which is why this is a cost and not a lie, but the headline bullet at `README.md:17` quotes only the flattering one and the resident figure arrives two lines later as "the difference being the shared GTK and WebKit libraries". Against a hard user requirement of ~100 MB, the honest headline is 213 MB and the engine floor is what `anon` measures. Fix: lead with `212.8 MB resident, 95.2 MB of it the browser's own` in the same clause, one point.
- **`anon_mb` excludes exactly the memory their own optimisation targets, and the suite has the field in hand.** `fn memory` reads `Pss` and `Pss_Anon` and skips `Pss_Shmem`, `Private_Dirty` and `SwapPss`, all of which are in the same smaps_rollup block (checked against `/proc/self/smaps_rollup`: `Pss_Shmem`, `Private_Dirty`, `Pss_Dirty`, `Anonymous` are all present). `src/main.rs:56-58` says the DMA-BUF buffers "are ordinary memory, and ordinary memory is what this browser is trying to spend less of" — if those buffers land in shared memory, `anon` is blind to the traffic they just rerouted, and there is no number in the report that would show it. 117.6 MB of the 212.8 PSS is `Pss_File`+`Pss_Shmem` (212.8 - 95.2) and never named. Fix: sum `Pss_Shmem` and `Private_Dirty` into the same dict and assert them, one point.
- **Every memory assertion is an absolute threshold the measured value clears by 30% to 280%, so none can catch the regression it exists to catch.** `idle one tab` asserts `anon_mb < 120` against a measured 95.2 and an observed range of 62.0-118.7 (`docs/LIMITS.md:36-38`) — the bar sits at the top of the noise band, so the worst measured run (118.7) nearly fails while a +24 MB regression passes. `20 tabs open` (`tools/stress.py:436-441`) asserts only `len(probe["tabs"]) >= len(ids)`; `per_tab_mb` is recorded and never asserted, so a tab costing 200 MB each passes and the `+20.6 MB per tab` row in `docs/LIMITS.md:32` is a figure with no assertion behind it. `tabs give their memory back` (`:448-453`) asserts `after_close["pss_mb"] < after["pss_mb"] - 100`, i.e. recovering 100 of the 414.7 MB opened, and never compares to `before` (212.8), so a 300 MB leak passes. `a memory spray is survived` (`:599`) asserts `pss_mb < 2600` against 1187.4. `the engine survives a spray` (`:603-606`) asserts `after["pss_mb"] < usage["pss_mb"] + 50`, so a browser still sitting at 1187 MB passes and the measured 408.2 is 2.8x under the bar. `memory comes back down` (`:981`) asserts `< 420` against 146.8. `nothing grows` (`:991-993`) allows 35 MB over 60 s, i.e. 35 MB/minute of leak passes, and it measures `pss` while the prose is about "own". Fix: make each bound proportional to a measured baseline: `per_tab_mb < 40`, `after_close["pss_mb"] < before["pss_mb"] + 60`, `after["pss_mb"] < 2 * self.one_tab["pss_mb"]` (2x212.8 = 425.6 vs measured 408.2, and 1187 fails by 3x), `< 260`, `drift < 10`. All five pass on the quoted run and all five would catch a real regression. One and a half points, the largest single item.
- **A figure in `docs/LIMITS.md` has no run behind it, and `--check` is green because that row is unmapped.** `docs/LIMITS.md:115` quotes the drift detail as `217.6MB -> 217.6MB (+0.0MB)`; the report writes `205.5MB -> 205.5MB`. `--check` prints `LIMITS.md agrees with the report` because the `RULES` table in `tools/report_figures.py:206-217` has no pattern for the label `nothing grows while nothing happens`, and `check()` only iterates `doc_rows` that map to a key. So the one row that says where its number comes from instead of which result produced it is also the one row the guard does not read. Fix: copy 205.5 into line 115 and add `(re.compile(r"^nothing grows", re.I), ["drift"])` with `put("drift", (by_name(report,"nothing grows while nothing happens") or {}).get("drift_mb"), ...)`. Half a point.
- **Two files on disk give contradictory four-run numbers for the same configuration.** `src/web.rs:85-91` says turning compositing off was "77.6-88.1 MB of the browser's own memory against 66.5-73.9 MB with it on". `src/main.rs:53-55` and `src/store.rs:66-72` say nothing set is 87.0/96.9/102.7/104.0 and the two always-on knobs give 60.4/75.1/75.2/87.8; 66.5-73.9 appears in no other document and matches neither arm, while the 77.6-88.1 arm is attributed there to compositing off *alone*, which `src/panels.rs:605` then attributes to the switch that also sets the other two. Fix: delete the 66.5-73.9 clause in `src/web.rs:90` and cite the `main.rs` table. Half a point.
- **The browser's main mechanism for giving memory back is never run.** `sleep_others` (`src/app.rs:1251-1290`) destroys the view and sets `asleep`, the timer ticks every 60 s (`:1296-1302`), and it is on by default at 30 minutes (`src/store.rs:99-100`). `docs/LIMITS.md:67` and `docs/ARCHITECTURE.md:156-158` promise it "returns the page's memory to the system". The suite's only sleep check (`tools/stress.py:926-928`) asserts that *restored* tabs come back asleep, which is `tab.asleep = url.is_none()` on restore, not the timer. Eleven runs and no run has ever watched a tab sleep, and the 30-minute default is untestable by hand. Because the suite already owns `XDG_CONFIG_HOME` (`tools/stress.py:141-142`), it can write `{"sleep_minutes": 1}` and prove it in 70 s. Half a point.
- **The idle number is one 3-second sample of one trivial page.** `tools/stress.py:406-409` loads `/plain` ("The quietest page there is", `tools/fixtures.py:82`) and reads memory 3 s after `wait_loaded`. The 62.0-118.7 spread across eleven runs is the same configuration, which says the sample itself is the noise; a second reading after the drift minute on the same tab would separate "settles" from "varies". Fix: record the idle dict twice, at 3 s and after the 60 s drift, and let `docs/LIMITS.md:35` say whether the range is the host or the settling. Quarter point.
- **The recovery is disclosed as complete and is not.** After the spray the tree settles at `pss 408.2` over `processes 9`, against `pss 212.8` over `processes 3` idle, i.e. closing one sprayed tab leaves 195 MB and six processes behind. `docs/LIMITS.md:131` says "that tab does, and closing it is the way back" — true as far as it goes; the report's own two numbers say the way back is only half a way back. Fix: one clause in `docs/LIMITS.md:129-132` quoting 408 against 213. Quarter point.

## The three changes that would raise this score most
1. Replace the six absolute memory thresholds with bounds derived from the measured baseline, so each one is a regression test rather than a formality: `per_tab_mb < 40` (measured 20.6) at `tools/stress.py:436`; compare `after_close` to the pre-open `before` plus 60 MB instead of `after - 100` at `:448`; `after["pss_mb"] < 2 * self.one_tab["pss_mb"]` at `:603`; `< 260` at `:981`; `drift < 10` at `:992`. All five pass on the current report and all five would fail a 2-3x regression.
2. Make the definition auditable and the reported figure match: add `Pss_Shmem` and `Private_Dirty` to `fn memory` (`tools/stress.py:71-78`) and print them, so the 117.6 MB that `anon` hides is named; fix `docs/LIMITS.md:115` from `217.6` to `205.5`; add the `nothing grows` label to `RULES` in `tools/report_figures.py:206-217` so `--check` finally reads the one row it skips; delete the unsupported `66.5-73.9` arm at `src/web.rs:90`.
3. Prove the sleep path instead of describing it: write `sleep_minutes: 1` into the suite's own `XDG_CONFIG_HOME` prefs, open two background tabs, wait 70 s, and assert `processes` and `anon_mb` fell and `probe` reports `asleep: true` for the inactive tab. That converts `docs/LIMITS.md:67` and `src/panels.rs:576-588` from a claim into the one memory behaviour a user can actually feel.
